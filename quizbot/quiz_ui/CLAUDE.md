# quizbot/quiz_ui/

Discord UI 화면들. `components/`(→ `components/CLAUDE.md`)에 버튼/모달/셀렉트메뉴 정의가 있고, 이 디렉터리 파일들은 그 컴포넌트를 조합한 화면(embed+components) 클래스.

## 프레임워크 (`common-ui.js`, `ui-system-core.js`)

- 모든 화면은 `QuizbotUI`(단순 메뉴) 또는 `QuizBotControlComponentUI`(페이지네이션 있는 목록, `prev`/`next`/`request_modal_page_jump` 처리 내장) 상속.
- `onInteractionCreate(interaction)`가 `new SomeUI(...)`를 반환하면 자동으로 화면 전환 + 이전 화면이 `prev_ui_stack`에 쌓임(뒤로가기용). `this`를 반환하면 같은 화면 유지하며 `update()`만. `undefined`면 아무 것도 안 함.
- `'back'` customId(컴포넌트: `only_back_comp`)는 `UIHolder`가 전역으로 가로채 자동 처리 — 개별 화면이 구현할 필요 없음.
- `UIHolder`: `UI_HOLDER_TYPE.PUBLIC`(길드 채널, `holder_id=guild_id`) / `PRIVATE`(DM, `holder_id=user_id`). `ui-system-core.js`의 `createXXXUIHolder` 함수들이 진입점(`createMainUIHolder`/`createQuizToolUIHolder`/`createAdminPanelUIHolder`).
- `onAwaked()`: 자식 화면에서 뒤로가기로 돌아왔을 때 호출됨(선택 개수/태그 텍스트 재계산 등에 씀).
- **주의**: `interaction.user.send(...)`(순수 DM 전송)에 `flags: MessageFlags.Ephemeral`을 줘도 아무 효과 없음(`flags`는 `interaction.reply`/`deferReply`/`followUp`같은 인터랙션 응답 전용) — 에페메럴로 보내려면 반드시 `interaction.reply(...)`(이미 reply를 소비한 인터랙션이면 `interaction.followUp(...)`) 사용할 것 (2026-08-08, B-2 피드백 1번에서 4곳 발견해 수정).
- **주의**: `SelectUIModeUI`/`MainUI` 등 "`return new XXXUI()`"로 화면을 전환하는 대부분의 `onInteractionCreate`는 새 화면을 `base_interaction.editReply()`(PUBLIC)/`base_message.edit()`(PRIVATE)로 그리므로, 정작 그 순간 클릭된 인터랙션 자체는 명시적으로 reply되지 않는 게 정상 동작(`bot.js` 전역 fallback이 `deferUpdate()`로 조용히 ack해줌) — 여기에 `interaction.explicit_replied`를 안 세웠다고 "버튼이 안 눌린다"고 오해하지 말 것(2026-08-13, uiHolder/quiz_session이 찾아졌는데도 fallback이 "만료됐어요" 안내를 잘못 띄우던 회귀를 고치며 이 동작을 다시 확인함 — 상세는 `docs/COMPLETED_WORK_LOG.md` 2026-08-13 항목).
- `createMainUIHolder`(`ui-system-core.ts`)는 길드에 이미 다른 유저의 화면(`MainUI`든 `WebHandoffUI`든 무관)이 떠 있으면 "권한 가져오기" 하이재킹 방어 안내(`force_take_comp`)를 띄운다(2026-08-13 일반화 — 원래는 `WebHandoffUI`일 때만 가드가 걸려서, 디스코드 UI 사용 중엔 다른 유저가 `/퀴즈`를 입력하면 확인 없이 곧장 화면을 가로챌 수 있었음). **요청자가 그 화면의 소유자 본인이면 이 가드를 건너뛰고** 새 `SelectUIModeUI`를 띄운다 — 본인이 다시 `/퀴즈`를 입력해 트랙을 바꾸는 건 하이재킹이 아니라 정상 요청이기 때문.
- `bot.js`의 `handle_ui_force_take`(2026-08-13, 예전 이름 `handle_web_handoff_force_take`)는 다른 유저가 "권한 가져오기"(`ui_force_take` customId) 버튼을 눌렀을 때 처리한다 — 이전 홀더를 `free()`(웹 세션이 있었다면 `UIHolder.free()`가 알아서 release IPC까지 보냄)한 뒤 `createMainUIHolder`를 그대로 재사용해 이 버튼 인터랙션으로 새 `SelectUIModeUI`를 띄운다. 예전엔 웹 세션 토큰을 IPC `force_take` 액션으로 미리 새로 발급받아 곧장 `WebHandoffUI`로 진입시켰지만, 디스코드 UI 사용 중에도 이 버튼이 뜨게 되면서 "웹 세션"이라는 특정 개념에 안 묶이도록 단순화됨.

## 진입/관리자 (직접 다뤄본 파일)

- **`main-ui.js`** — 메인 메뉴(`MainUI`). 죽은 코드였던 `loadVersionInfo()`(설정에서 이미 비활성화된 기능)는 삭제됨.
- **`quiz-tool-guide-ui.js`** — "퀴즈 만들기" 안내 화면, 정적 안내문 + 뒤로가기만.
- **`note-select-ui.js`** — 공지/패치노트 목록. 패치노트(`patch_note_contents`)는 실제로는 채워지지 않는
  죽은 기능(2026-08-12 확인, "더 이상 안 씀"이 사용자 확인 방침 — 고칠 계획 없음). 목록 로딩 로직은
  `managers/notice_manager.ts`의 `loadNoticeList`로 추출됨(나머지 화면 웹 포팅, 아래 참고).
- **`user-quiz-list-ui.js`** — 내 퀴즈 목록(`UserQuizListUI`). 생성자 2번째 인자 `show_all_quizzes`(기본 false) — true면 전체 유저 퀴즈 조회(관리자 패널 전용). `show_all_quizzes=false`로 호출되면 자기 퀴즈만 봄. `/퀴즈만들기`(`createQuizToolUIHolder`)의 최초 화면은 2026-08-11부터 이 UI가 아니라 `QuizEditSelectUIModeUI`(아래) — 디스코드 UI 선택 시 이 UI로 진입(동작 동일).
- **`user-quiz-info.ui.js`** — 유저 퀴즈 상세/편집(`UserQuizInfoUI`). 삭제 버튼이 `interaction.user.id === PRIVATE_CONFIG.ADMIN_ID` 여부로 `quiz_delete_confirm_comp`(일반, 2버튼) vs `quiz_delete_confirm_admin_comp`(관리자, 3버튼: 취소/삭제/삭제+영구밴) 분기. `onReceivedWebSessionSignal`/`reapplyFromWebPayload`(퀴즈 선택 웹 연동 Phase 2, 2026-08-08 신설) — `dev-quiz-info-ui.js`와 동일 패턴(확정 후 웹에서 재선택 시 같은 인스턴스를 갱신, 새 인스턴스 반환 안 함)이지만 DB 조회가 필요해 비동기(fire-and-forget 후 `refreshUI()`+`fillInfoAsDevQuizInfo()`를 직접 호출). 마지막 반영은 **`update()`가 아니라 `sendDelayedUI(this, true)`(강제 재전송, 2026-08-15 수정)** — 재선택한 퀴즈의 썸네일이 이전 퀴즈와 다를 수 있는데, Discord embed edit로는 새 이미지 URL이 간헐적으로 안 불러와지는 버그가 있어서(`user-question-info-ui.js`의 "24.05.07 embed 이미지 버그"와 동일 원인) `update()`를 쓰면 이미지가 안 바뀐 채로 보일 수 있었음. `quiz_toggle_public` 핸들러의 "태그 1개 이상 있어야 공개 전환 가능" 조건은 2026-08-11부터 `quiz_editor_validation.canGoPublic(tags_value)` 호출로 바뀜(퀴즈 만들기 웹 연동 Phase 2, 아래 `user-question-info-ui.js` 항목 참고).
- **`quiz_editor_validation.ts`**(`quizbot/managers/`, 신규 2026-08-11) — 퀴즈 만들기 웹 연동
  (`docs/plans/WEB_QUIZ_CREATION_PLAN.md`) Phase 2. `user-question-info-ui.js`/`user-quiz-info.ui.js`의
  인터랙션-비의존 검증/파싱 순수 함수 7개(`parseAudioRangePoints`/`redefineRepeatCount`/
  `parseUseAnswerTimer`/`isValidAudioUrl`/`isValidImageUrl`/`isDiscordCdnLink`/`canGoPublic`)를 모아둔
  공유 모듈 — `multiplayer_mmr.js`와 동일 관례. 디스코드 UI가 지금 이 함수들을 호출하고, Phase 3~4의
  REST 핸들러(`web_quiz_editor_routes.ts`)도 같은 함수를 재사용할 예정.
- **`multiplayer-quiz-select-ui.js`** — 멀티플레이 로비 생성/참가 진입점. `checkMultiplayerBanMessage(interaction)`(2026-08-12, UI 개선 2라운드 B-5 — 원래 이름 `checkMultiplayerBan(list)`)이 `ban_manager.isBanned(...)`로 위임하되, 유저ID/길드ID를 따로 검사해서 어느 쪽이 밴됐는지 구분하는 메시지(+문의처 안내)를 반환한다 — 예전엔 `[guild.id, user.id]`를 한 배열로 묶어 검사해서 "당신 또는 이 서버가..."로 뭉뚱그려 안내했음. 같은 증상이 있는 `web-handoff-ui.ts`의 `buildMultiplayerUI`(웹 경로)는 아직 안 고침.
- **`admin-panel-ui.js`**/**`admin-ban-list-ui.js`** — `/quizmgr` 관리자 패널(밴 목록 관리/신고처리/퀴즈 관리). 다른 유저는 절대 접근 불가하도록 다층 방어(루트 `CLAUDE.md`의 "관리자 전용 기능" 참고).

## 그 외 화면 (탐색 결과 요약)

**퀴즈 선택/시작 흐름**
- **`select-ui-mode-ui.js`** (신규, 2026-08-08) — `/퀴즈` 최초 진입 화면(`ui-system-core.js`의 `createMainUIHolder`가 `MainUI` 대신 이걸 먼저 띄움). "디스코드 UI"/"웹 UI" 두 트랙 분기: `'1'`(디스코드) → `MainUI`(기존 방식 100% 그대로), `'2'`(웹) → `MainUI`/`SelectQuizTypeUI`를 건너뛰고 곧장 `WebHandoffUI('dev', interaction)`(원격 컨트롤). `'dev'`는 세션 생성 시 초기 탭일 뿐 세션이 그 모드에 고정되는 건 아님 — 웹 프론트엔드에서 유저 퀴즈/랜덤 퀴즈 탭으로 전환해도 정상 동작함(Phase 1/2/3 전부 완료, 아래 `web-handoff-ui.js` 참고). 버튼 컴포넌트(`components/base_components.ts`의 `select_ui_mode_btn_component`, `quiz-edit-select-ui-mode-ui.ts`와 공유)는 2026-08-12부터 라벨이 `'디스코드 UI'`/`'웹 UI'` 텍스트(이전엔 숫자 `'1'`/`'2'`뿐) — `customId`는 그대로 `'1'`/`'2'`. 상세는 `docs/plans/WEB_INTEGRATION_PLAN.md`. **2026-08-13** — 실시간 공지(`resources/current_notice.txt`)를 `bot.js`가 `/퀴즈` 처리 중 별도 `channel.send()`로 보내던 걸 이 화면의 embed 필드(`buildNoticeFields()`)로 옮김 — 트랙 선택 전에만 뜨는 화면이라 웹 UI 선택 후에는 자동으로 안 보임. 설명과 공지 사이 시각적 구분을 위해 빈 이름(zero-width space) + 가로줄 문자 필드를 구분선으로 추가. "권한 가져오기"(`ui_force_take`, 아래 `createMainUIHolder` 항목)로 다른 유저에게서 화면을 넘겨받은 경우도 이 화면이 뜬다 — 별도 인자 없이 일반 `/퀴즈` 진입과 완전히 동일하게 동작(웹 UI를 고르면 새 세션을 그냥 새로 발급받음, 재사용 안 함 — 애초에 이전 홀더가 이미 `free()`돼서 재사용할 대상이 없기도 하고, 재사용해봐야 절약되는 비용이 미미해서 단순한 쪽을 선택함).
- **`select-quiz-type-ui.js`** — "개발자 퀴즈/유저 제작 퀴즈/오마카세 퀴즈" 선택 (main-ui의 '3'번에서 진입). **디스코드 트랙 전용 화면이라 웹 연동과 무관** — `'1'`(공식)은 다시 `DevQuizSelectUI`로 원복됨(2026-08-08, 투트랙 분리 — 예전엔 여기서 `WebHandoffUI`로 가로챘었지만 그 진입점이 `select-ui-mode-ui.js`로 위로 옮겨감). Phase 2(유저 퀴즈 웹 연동) 작업도 이 파일을 건드리지 않음 — 웹 쪽 유저 퀴즈 지원은 전부 `select-ui-mode-ui.js`→`WebHandoffUI` 경로에서 처리됨.
- **`quiz-edit-select-ui-mode-ui.ts`**/**`quiz-edit-web-handoff-ui.ts`** (신규, 2026-08-11) — 퀴즈 만들기 웹 연동(`docs/plans/WEB_QUIZ_CREATION_PLAN.md`) Phase 1. `select-ui-mode-ui.ts`/`web-handoff-ui.ts`와 같은 투트랙 진입 패턴이되 `/퀴즈만들기`(`createQuizToolUIHolder`)가 항상 DM(PRIVATE, holder_id=user_id)에서만 호출되므로 하이재킹 방어(force_take/already_locked)가 통째로 빠짐 — DM은 봇-유저 1:1이라 애초에 다른 유저가 이 화면을 볼 수 없다. `QuizEditWebHandoffUI`는 마스터의 `web_session_manager`에 `create_owner_session`(owner_id 단위 세션, guild 개념 없음) IPC 요청을 보내고, 편집 링크 Link 버튼 1개로 잠금 화면을 구성한다. Phase 1은 아직 실제 편집 화면이 없어 `onReceivedWebSessionSignal`이 `'expired'`만 처리(`applied`는 문제/퀴즈 CRUD가 붙는 Phase 3~4에서 추가 예정).
- **`web-handoff-ui.js`** (신규, 2026-08-08) — 퀴즈 선택 웹 연동(`docs/plans/WEB_INTEGRATION_PLAN.md`) 잠금 화면. `select-ui-mode-ui.js`의 "웹 UI" 버튼에서 진입(이전엔 `select-quiz-type-ui.js`의 '공식 퀴즈' 버튼에서 진입했었음 — 뒤로가기/GC만료 복귀 대상 화면도 그에 맞춰 `SelectQuizTypeUI`→`SelectUIModeUI`로 바뀜). 마스터의 `web_session_manager`와 `WEB_SESSION_REQUEST`/`WEB_SESSION_SIGNAL` IPC로만 통신, 실제 세션 상태는 안 갖고 있음. `onReceivedWebSessionSignal`이 `updated`(선택 요약 갱신)/`applied`(다음 UI로 전환, `handleApplied`)/`expired`(`goToBack()`)를 처리 — `applied`에서 DB 조회가 필요한 모드(유저 퀴즈)는 `UIHolder.on()`이 동기 계약이라 `this.holder.appendNewUI()`/`updateUI()`를 직접 호출하는 우회가 필요함(dev/omakase 모드는 동기 데이터라 이 우회가 없음). **`handleApplied`는 `this.mode`(세션 생성 시 고정값)가 아니라 `payload.mode`로 분기한다**(2026-08-08 Phase 2 - 프론트엔드가 select/confirm 요청마다 자기 탭의 mode를 실어보내므로, 한 세션에서 dev/user/omakase 탭을 자유롭게 오갈 수 있음). `buildUserQuizInfoUI(payload)`(Phase 2, 비동기) — `loadUserQuizInfoById`로 조회 후 `UserQuizInfoUI` 생성, `quiz_info['selected_question_count']`를 `onReady()` 호출 전에 미리 채워서 기본값(전체 문제 수)으로 덮어써지지 않게 함. `buildOmakaseQuizInfoUI(payload)`(Phase 3, 2026-08-08 신규, 동기) — DB 조회가 필요 없는 작은 데이터라 dev와 동일하게 즉시 반환, `OmakaseQuizRoomUI.buildOmakaseQuizInfoFromWebPayload`로 조립하고 `QuizInfoUI.BASKET_CACHE`도 같이 갱신. `buildMultiplayerUI(payload)`(Phase 4, 2026-08-10 신규, 비동기) — `MultiplayerQuizSelectUI.createLobby`/`tryJoinLobby`와 동일한 밴 체크(`ban_manager.isBanned`)/음성채널 체크(`quiz_system.checkReadyForStartQuiz`)를 그 클래스를 거치지 않고 직접 재현한다(음성채널 체크는 진짜 `GuildMember.voice`가 필요해 `guild.members.fetch`로 실제 멤버를 조회 - `{member:{id}}` 같은 최소 어댑터로는 불가능). 통과하면 `{guild, member, channel, web_mode:true}` 어댑터로 `MultiplayerQuizLobbyUI`를 직접 생성(`action:'create'`는 `MultiplayerQuizLobbyUI.buildMultiplayerQuizInfoFromWebPayload`로 quiz_info 조립, `action:'join'`은 `payload.session_id`로 참가) - `MultiplayerQuizLobbyUI` require는 함수 안으로 미룸(아래 항목 참고, dev-quiz-info-ui.js 순환 require 수정과 동일한 이유). **주의**: "선택 완료(applied)"는 토큰을 파기하지 않음(2026-08-08 재설계) — 화면은 `DevQuizInfoUI`/`UserQuizInfoUI`/`OmakaseQuizRoomUI`/`MultiplayerQuizLobbyUI`로 넘어가지만 웹 세션은 계속 살아있고, 그 뒤 재선택은 각 정보 화면이 처리함(아래). **밴/음성채널 체크 실패 시 `goToBack()`을 부르지 않음**(2026-08-10 실사용 피드백 수정 - 원래 `goToBack()`을 불렀는데, `WebHandoffUI` 자신이 `prev_ui_stack`의 이전 화면(`SelectUIModeUI`)으로 교체돼버려서 이후 웹에서 재시도해도 신호를 받을 화면이 없어 완전히 먹통이 됐었음). 대신 `this.last_error`를 채우고 `refreshLockedEmbed()`로 잠금 화면에 실패 사유를 얹어 보여주면서 `WebHandoffUI`를 유지 - 재시도가 정상 동작함. 성공/실패 여부는 `ipc_manager.sendWebSessionRequest({action:'report_multiplayer_result', ...})`로 마스터의 `web_session_manager`에 보고되고, 프론트엔드는 `/api/multiplayer-result`를 잠깐 폴링해서 실제 결과를 읽어온다(웹에도 진짜 에러 메시지가 뜨게 됨) - 다만 이건 밴/음성채널 체크(사전 검증) 결과만 보고하고, 그 이후 `MultiplayerQuizLobbyUI` 내부의 딥 IPC(실제 로비 생성/참가) 실패는 낙관적으로 성공 취급(드문 케이스, 그 시점엔 이미 `MultiplayerQuizLobbyUI`가 `prev_ui_stack`에 `WebHandoffUI`를 쌓아둔 채라 실패해도 자체 `goToBack()`으로 안전하게 복귀됨). 로비 생성 후에도 웹에서 계속 설정을 바꿔 재확정할 수 있다(2026-08-10 피드백) - 프론트엔드(`MultiplayerTab.jsx`)가 최초 생성 후엔 "대기실 목록으로"를 숨기고 같은 화면에서 계속 `confirmMultiplayer('create', ...)`를 재호출, 이 신호는 이미 `MultiplayerQuizLobbyUI`가 current UI라 `WebHandoffUI.buildMultiplayerUI`를 다시 거치지 않고 `MultiplayerQuizLobbyUI.onReceivedWebSessionSignal`이 직접 처리함(밴/음성채널 재검증 없음, 기존 Omakase와 동일 패턴). **여전히 남은 한계**: 생성 폼은 설정을 만지는 동안 실시간 미리보기(select 브로드캐스트)가 없어 확정을 눌러야만 디스코드에 반영됨. **`refreshLockedEmbed`(2026-08-12, 웹 API 보안 점검 심화 조사)**: `current_selection.title`(`POST /api/session/select`의 진행 중 미리보기 payload, 서버에서 길이 검증을 안 함)을 그대로 이 길드의 공유 embed에 꽂고 있었음 — UI를 거치지 않고 직접 API를 호출하면 임의 길이의 문자열을 다른 길드원에게 보이는 화면에 넣을 수 있었던 지점이라 표시 직전에 60자로 자르도록 수정.
