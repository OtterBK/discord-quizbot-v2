# quizbot/managers/db/

`db_manager.js`(상위 디렉터리)가 이 폴더 전체를 spread로 재수출하는 facade. 원본은 500줄짜리 `db_manager.js` 하나였고, 테이블/도메인별로 분리됨. **`sendQuery`는 `db_core.js`에서만 쓰이고 facade에는 재수출되지 않음** (원본에 없던 함수라 API 표면을 그대로 유지하기 위함) — 새 도메인 파일을 추가할 땐 `db_core.js`를 require해서 `db_core.sendQuery(...)`를 쓰면 됨.

- **`db_core.js`** — `pg.Pool` 생성, `sendQuery(query_string, values)`(내부 헬퍼, 연결 안 됐으면 조용히 `undefined` 반환 — 에러를 던지지 않음), `initialize()`(풀 연결), `executeQuery(query, values)`(트랜잭션 등에서 직접 쓰는 raw 버전).
- **`db_option.js`** — 서버별 옵션(`tb_option`). **주의**: `selectOption`/`updateOption`은 파라미터화 쿼리(`$1`)가 아니라 문자열 직접 삽입 방식 — 원본 주석에 "옵션쪽은 어차피 고정값이니깐 placeholder 사용하지 말자, 건드리기 두렵다"고 적혀있음. 여기 손댈 때 SQL 인젝션 여지 있는지 특히 조심. `updateOptionParameterized(guild_id, option_data)`(나머지 화면 웹 포팅, 2026-08-12 신설)는 서버 설정 웹 API(`web/web_express_app.ts`의 `PUT /api/server-option`) 전용 — 위 두 함수(디스코드 경로)는 그대로 두고, 이 함수만 `$n` 플레이스홀더로 새로 작성됨. 호출부가 `text_contents.json`의 `select_menu` 화이트리스트로 필드명/값을 이미 검증한 뒤 넘기는 걸 전제로 컬럼명을 보간한다.
- **`db_quiz.js`** — 유저 퀴즈/문제 CRUD, 좋아요, 인증(certify), 태그/장바구니 기반 랜덤 문제 선택(`selectRandomQuestionListByTags`/`selectRandomQuestionListByBasket`). 가장 큰 파일 — 원본에서 "User Quiz info"와 "User QuestioN Info" 관련 함수가 서로 섞여 있던 순서를 그대로 유지했음(임의로 재배열 안 함). `selectQuizInfoById(quiz_id)`(퀴즈 선택 웹 연동 Phase 2, 2026-08-08 신설)는 quiz_id 단건 조회 - 기존엔 전체(`selectAllQuizInfo`)/creator별(`selectQuizInfo`) 조회만 있었음. `selectOwnedQuizInfoById(quiz_id, creator_id)`(퀴즈 만들기 웹 연동 Phase 3, 2026-08-11 신설)는 `selectQuizInfoById`와 다르게 `is_private` 필터가 없는 대신 `creator_id`로 소유권을 DB 레벨에서 강제 - 웹 편집기가 `/quiz/:quizId`로 직접 딥링크할 때 다른 유저의 비공개 퀴즈가 노출되지 않게 하는 핵심 방어(`quizbot/managers/web/web_quiz_editor_routes.ts`의 `requireQuizOwnership`이 이 함수로 소유권 검증까지 겸함). `updateQuizInfo`/`updateQuestionInfo`(2026-08-12, 웹 API 보안 점검 SQL 하드닝)는 `quiz_id`/`question_id`를 쿼리 문자열에 직접 보간하던 걸 마지막 `$n` 플레이스홀더로 교체 - 호출 경로상 항상 `parseInt`를 거친 정수만 들어와 실질적 위험은 없었지만 방어적인 코드가 아니었음. **`selectRandomQuestionListByBasket`(같은 날, 추가 심화 점검에서 발견된 실제 SQL 인젝션)**: 원래 `basket_condition_query: string`을 `WHERE quiz_id IN ${...}`에 그대로 문자열 보간했음 — 디스코드 전용이던 시절엔 항상 DB에서 읽은 실제 정수로만 조립돼 무해했지만, 퀴즈 선택 웹 연동(`POST /api/session/confirm`)이 `basket_items`를 서버 검증 없이 그대로 받게 되면서 임의 문자열이 도달할 수 있는 실제 취약점이 됐음 — `quiz_id_list: number[]`를 받아 `WHERE quiz_id = ANY($1::int[])`로 파라미터화(호출부 `quiz_system/lifecycle/initialize.ts`의 `OmakaseQuizInitialize`도 실제로 쓰기 직전 정수 필터링 추가, 상세는 `quiz_system/CLAUDE.md`). **같은 날 후속 수정(소유권/공개여부 검사 추가)**: SQL 인젝션은 막혔지만 `is_private`/`is_use` 필터가 없어서, 웹 API를 프론트엔드 없이 직접 호출하면(정상 UI 흐름은 항상 공개 퀴즈만 담기지만 API 자체는 basket_items의 quiz_id를 검증하지 않음) 순차 발급되는 quiz_id를 추측해 다른 유저의 비공개 퀴즈를 출제시킬 수 있었음 — 짝 함수 `selectRandomQuestionListByTags`와 동일하게 CTE에 `and is_private = false`, `and is_use = true` 추가.
- **`db_random_quiz_preset.ts`**(랜덤 퀴즈 프리셋, 2026-08-13 신설, `docs/plans/RANDOM_QUIZ_PRESET_PLAN.md`) — 웹 UI 한정 기능. `tb_random_quiz_preset`(메타)/`tb_random_quiz_preset_item`(항목, `sort_order`로 순서 보존) 두 테이블 — 기존 스키마에 배열 컬럼 선례가 없어 `tb_like_info`류 연결 테이블 패턴을 그대로 따름. `insertRandomQuizPreset`은 트랜잭션 없이 2단계 INSERT(이 코드베이스가 다단계 저장을 트랜잭션으로 묶는 관행 자체가 없음)라 item 삽입 실패 시 방금 만든 빈 preset 행을 직접 정리해서 고아 방지. `deleteRandomQuizPreset`은 `user_id`까지 조건에 넣어 소유권을 DB 레벨에서 강제(`selectOwnedQuizInfoById`와 동일 관행).
- **`db_report.js`** — 신고 처리 관련(`tb_chat_info`, `tb_report_info`, `tb_ban_history`). `report/CLAUDE.md`의 신고 흐름과 짝을 이룸.
- **`db_scoreboard.ts`** — 멀티플레이 글로벌 스코어보드(`tb_global_scoreboard`, win/lose/mmr). `selectTop50Scoreboard`(2026-08-15 이전 이름 `selectTop10Scoreboard` — TOP50 노출 요청으로 개명+`LIMIT 50`, 같은 날 후속)는 상위 50개 조회. **시즌 아카이브(2026-08-15 신설, `docs/plans/SCOREBOARD_SEASON_PLAN.md`)**: `selectSeasonList`/`selectArchivedTop50Scoreboard`/`selectArchivedGuildScoreboard`/`endCurrentSeason` 4개 추가 — 핫패스 테이블인 `tb_global_scoreboard`는 건드리지 않고, 신규 테이블 `tb_scoreboard_season`(시즌 메타)/`tb_global_scoreboard_archive`(시즌 종료 시점 스냅샷)로 별도 관리한다. 이 코드베이스에 트랜잭션 헬퍼가 없어(`db_random_quiz_preset.ts`와 동일 관행) `endCurrentSeason`은 시즌 행 INSERT → 스코어보드 스냅샷 INSERT...SELECT → 라이브 테이블 DELETE 순서로 진행하고, 스냅샷 단계가 실패하면 방금 만든 시즌 행을 보상 DELETE로 정리한다. DDL은 마이그레이션 프레임워크가 없어 `docs/plans/SCOREBOARD_SEASON_PLAN.md`에 psql로 수동 실행할 스크립트로 적어뒀고 `auto_script/db_backup/base.sql`에도 반영됨 — **DDL을 실행하기 전까지는 이 4개 함수가 전부 조용히 `undefined`를 반환**(`db_core.sendQuery`의 에러 흡수 동작), 위 계층(`scoreboard_season_manager.ts`/`quiz_ui/scoreboard-ui.ts`/`web_express_app.ts`)은 이를 "시즌 없음"으로 취급해 기존 동작(현재 시즌만 표시)으로 자연스럽게 폴백한다.
