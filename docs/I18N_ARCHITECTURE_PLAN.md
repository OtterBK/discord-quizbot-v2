# 다국어(i18n) 지원 아키텍처 계획서

> **상태: 조사/설계 단계 문서. 코드는 아직 전혀 수정하지 않았음.** 사용자가 명시적으로 진행을 지시하기 전까지
> 이 문서에 적힌 어떤 항목도 구현하지 않는다.
>
> 배경: 지금까지 두 라운드(`UI_IMPROVEMENT_PROPOSAL.md`, `UI_IMPROVEMENT_PLAN_ROUND2.md`)에 걸쳐 UI 텍스트를
> 손보면서, 문구 대부분이 `config/text_contents.json` 한 곳이 아니라 각 화면 파일에 직접 하드코딩돼 있다는 게
> 반복적으로 확인됐음. 이 상태로는 나중에 두 번째 언어를 추가하려 해도 "어디를 고쳐야 하는지" 자체를 찾는 게
> 일이라, 다국어 지원을 위한 아키텍처를 미리 검토해달라는 요청에 따라 작성.

---

## 1. 현재 상태 조사 결과

### 1-1. `text_contents.json`은 이미 다국어를 염두에 두고 설계는 돼 있었음

```json
{ "kor": { "main_menu": { ... }, "server_setting_ui": { ... }, ... 19개 섹션 } }
```

소비 코드도 전부 `require('.../text_contents.json')[SYSTEM_CONFIG.LANGUAGE]` 형태(`SYSTEM_CONFIG.LANGUAGE = 'kor'`)로,
언어 키로 한 번 인덱싱하는 구조 자체는 갖춰져 있음. 즉 "언어별로 텍스트 묶음을 나눈다"는 아이디어는 원래
설계에 이미 있었던 셈. 문제는 아래 두 가지.

### 1-2. 문제 ①: 실제로는 텍스트 대부분이 이 파일 밖에 하드코딩돼 있음

`quizbot/` 전체 92개 JS 파일 중 한글이 포함된 파일이 92개(사실상 전부, 주석/로그 포함). 이번 세션에서 UI
텍스트를 두 라운드에 걸쳐 손보면서 직접 확인한 것만 나열해도:

- 버튼 라벨/모달 제목/placeholder — `quiz_ui/components/*.js` 전체가 `ButtonBuilder`/`TextInputBuilder`에
  문자열을 직접 박아넣는 방식(`text_contents.json`을 아예 안 씀).
- 화면별 에러/성공 메시지 — `report_submission.js`, `feedback_manager.js`, `multiplayer-quiz-lobby-ui.js`,
  `admin-ban-list-ui.js` 등 절대다수가 인라인 템플릿 리터럴.
- 화면 전체가 `text_contents.json`에 항목이 아예 없는 경우도 있음 — `scoreboard-ui.js`, `note-ui.js`는
  `scoreboard_ui`/`note_ui` 섹션이 아예 존재하지 않아 100% 하드코딩.
- 날짜 포맷도 `'ko-KR'`이 직접 박혀있음 (`user-quiz-info.ui.js`의
  `birthtime.toLocaleDateString('ko-KR', {...})` 등) — 텍스트가 아니어도 로케일에 의존하는 지점.

즉 `SYSTEM_CONFIG.LANGUAGE`를 `'eng'`로 바꿔도 실제로 화면에 보이는 문구 중 상당수(정확한 비율은 안 세봤지만,
지금까지 검토한 화면 기준 절반 이상)는 여전히 한국어 그대로 남는다. **이게 가장 큰 실질적 장벽.**

### 1-3. 문제 ②: `LANGUAGE`가 "요청 단위"가 아니라 "프로세스 전역 상수"

```js
// 대부분의 quiz_ui/*.js 파일 최상단
const text_contents = require('../../config/text_contents.json')[SYSTEM_CONFIG.LANGUAGE];
```

이 패턴이 **require 시점(=서버 최초 기동 시점)에 딱 한 번** 평가돼서 모듈 스코프 상수(`const`)로 굳어버림.
즉 지금 구조로는:

- 서버(길드)마다 다른 언어를 쓰게 할 수 없음 — 봇 프로세스 전체가 항상 같은 언어.
- 유저마다 다른 언어를 쓰게 할 수도 없음(퀴즈 만들기 DM 등).
- `SYSTEM_CONFIG.LANGUAGE`를 바꾸려면 **코드/설정 배포 + 봇 재시작**이 필요함.

한국 커뮤니티 대상 봇이라 지금까지는 이게 전혀 문제가 안 됐지만, "다국어 지원"이 실제로 의미하는 게
**"영어 서버와 한국어 서버가 동시에 각자 언어로 쓸 수 있어야 한다"**라면, 텍스트를 옮기는 것만으로는
해결이 안 되고 이 구조 자체를 바꿔야 함.

### 1-4. 부차적 문제: 플레이스홀더 치환 방식이 번역 친화적이지 않음

`text_contents.json`에서 `${var}`가 들어간 텍스트가 최소 14개 확인됨(`.replace("${var}", value)` 패턴).
이 방식의 한계:

- `String.replace()`는 **첫 번째로 발견된 자리만** 바꿈(전역 치환 아님) — 같은 변수를 문장에 두 번 넣고 싶으면
  현재 방식으론 안 됨.
- 언어마다 어순이 다름(한국어 SOV vs 영어 SVO) — 지금처럼 "고정된 문장 틀에 값만 끼워넣는" 방식은 번역 시
  자연스러운 문장이 안 나올 수 있음. 예: `"${target}을(를) 추방하였습니다"` 같은 조사(을/를, 이/가, 로/으로)
  처리도 지금은 아예 없음(오늘 작업한 것도 포함해서 "사용로", "무제한로"처럼 어색한 경우가 이미 있음 —
  다국어와는 별개로 존재하던 기존 흠).
- 결론: 새 언어를 추가할 거면 이 참에 "고정 문장 + 값 치환"이 아니라 **언어별로 완전한 문장을 따로 쓰는**
  방식으로 가는 게 번역 품질 면에서 안전함(ICU MessageFormat류가 이 문제를 표준적으로 해결함).

### 1-5. Discord 쪽에서 이미 제공하는 것

- `interaction.locale`(요청을 보낸 유저의 디스코드 클라이언트 언어), `interaction.guild.preferredLocale`
  (서버 설정 언어) — 매 인터랙션마다 자동으로 따라옴. 유저가 직접 설정 안 해도 "그럴듯한 기본값"을 추측하는
  용도로 쓸 수 있음.
- `SlashCommandBuilder.setNameLocalizations()`/`setDescriptionLocalizations()` — 슬래시커맨드 이름/설명 자체를
  디스코드가 유저 클라이언트 언어에 맞게 자동으로 보여주는 **discord.js 내장 기능**. 지금 `command_manager.js`는
  전혀 안 쓰고 있음 — 커맨드 이름/설명 다국어화는 이 기능으로 별도 처리 가능(봇 자체 텍스트 시스템과는 무관).

## 2. 아키텍처 옵션

### 옵션 A. 최소 변경 — 지금 구조 유지, 텍스트만 이전

`text_contents.json`에 `eng` 같은 새 최상위 키를 추가하고, 하드코딩된 문구들을 전부 이 파일로 옮기는 것까지만
한다. `SYSTEM_CONFIG.LANGUAGE` 상수는 그대로 둔다(여전히 프로세스 전역, 재시작해야 바뀜).

- 장점: 코드 변경 폭이 제일 작음. 기존 `text_contents.json[LANGUAGE]` 패턴과 완전히 동일해서 새로 배울 것도 없음.
- 단점: 문제 ②(서버/유저별 동시 다국어)가 전혀 해결 안 됨. "한국어 봇을 영어로 통째로 바꿔서 운영"은 되지만
  "한국 서버는 한국어로, 해외 서버는 영어로 동시에" 쓰는 건 여전히 불가능.
- 적합한 경우: 애초에 목표가 "동시 다국어"가 아니라 "필요하면 언젠가 영어 버전을 별도로 띄울 수 있게
  대비"하는 정도라면 이걸로 충분함.

### 옵션 B. 완전한 런타임 다국어 — locale을 요청마다 넘기는 구조로 전환

`const text_contents = require(...)[LANGUAGE]`(모듈 스코프 상수)를 없애고, 대신 텍스트를 가져올 때마다
"이번 요청은 어떤 locale인지"를 넘겨받는 함수 형태로 바꾼다. 예: `t('quiz_maker_ui.confirm_quiz_delete', locale)`.
locale은 길드별 설정값(신규 서버 옵션 "언어")이나 유저별 설정값에서 매 요청마다 조회.

- 장점: 실제로 서버/유저마다 다른 언어를 동시에 쓸 수 있음. 진짜 의미의 "다국어 지원".
- 단점: 영향 범위가 큼 — `text_contents`를 최상단에서 require하는 파일이 20개 이상, 여기에 하드코딩된
  텍스트를 옮기면서 새로 함수 호출로 바꿔야 하는 지점까지 합치면 실질적으로 **quiz_ui/ 거의 전체 + 일부
  managers/**를 건드리게 됨. 화면 클래스 생성자에 `locale`을 추가로 넘겨야 하는 경우도 많음(현재
  `guild_id`만 받는 클래스들).
- 적합한 경우: 처음부터 "동시 다국어"가 목표라면 결국 이 구조로 가야 함. A로 먼저 갔다가 나중에 B로
  옮기는 것도 가능하지만, 텍스트 이전 작업을 두 번 하게 되는 비효율이 있음.

### 옵션 C (권장). 단계적 접근 — 처음부터 B를 겨냥하되 단계로 쪼갬

A와 B는 사실 "어디까지 할 거냐"의 차이지, 서로 다른 길이 아님. 텍스트를 한 곳으로 모으는 작업(A의 핵심)은
B로 가더라도 어차피 해야 하는 선행 작업이라, 처음부터 "나중에 locale 파라미터화하기 쉬운 형태"로 모아두면
낭비가 없음. 아래 "3. 권장 실행 계획"이 이 옵션의 상세.

## 3. 권장 실행 계획 (옵션 C, 4단계)

### Stage 1 — 텍스트 인벤토리 확보 + 리소스 파일 통합

- `quizbot/` 전체를 훑어서 사용자에게 보이는 문자열(버튼 라벨, 모달 제목/필드/placeholder, 임베드
  텍스트, 성공/실패 메시지)을 전부 `text_contents.json`(또는 언어별 파일로 쪼갠 `locales/kor.json` 형태로
  전환)로 옮긴다. 로그 메시지(`logger.info/error` 등)와 개발자 주석은 **대상 아님**(사용자에게 안 보임).
- 이 단계에서 파일 구조도 같이 정리하는 걸 권장: 지금처럼 파일 하나(`text_contents.json`)에 언어별로
  다 몰아넣기보다, `locales/kor.json`, `locales/eng.json`처럼 **언어별로 파일을 분리**하면 (a) 번역가에게
  파일 하나만 넘기면 되고 (b) 나중에 언어 추가 시 diff가 깔끔함.
- 규모가 크다(90개 넘는 파일에 흩어져 있음) — 한 번에 몰아서 하기보다 **화면/기능 단위로 나눠서 여러
  커밋에 걸쳐 진행**하는 걸 권장. 이미 리팩터(REFACTOR_PLAN.md)나 UI 개선 라운드에서 썼던 "영역별로 쪼개서
  진행 + 매 단계 테스트/린트 통과 확인" 방식을 그대로 재사용하면 됨.
- 이 단계만으로는 실제 언어 전환 기능은 안 생기지만, "번역하려면 파일 하나만 채우면 되는" 상태가 됨.

### Stage 2 — 조회 방식을 함수 호출로 전환 (`t()` 헬퍼 도입)

- 새 모듈(예: `utility/i18n.js` 또는 `utility/util/locale_utility.js` — 기존 `utility/util/` 분리 컨벤션에
  맞춤) 하나를 만들어서 `t(locale, key_path, params)` 형태의 조회 함수를 제공.
  - `key_path`는 지금처럼 점 표기(`'quiz_maker_ui.confirm_quiz_delete'`)로.
  - `params`로 치환값을 넘기되, 지금의 `.replace("${var}", ...)` 대신 **정규식 기반 전역 치환**(같은 변수
    여러 번 등장 지원) 정도는 최소한으로 개선.
  - 요청한 `locale`에 해당 키가 없으면 `kor`(기본 언어)로 **폴백** — 번역이 덜 된 언어라도 화면이 깨지지
    않고 최소한 한국어로라도 보이게.
  - 외부 라이브러리(i18next 등)를 새로 들여오는 것보다, 지금 코드베이스 스타일(CommonJS, 의존성 최소,
    직접 짠 유틸 함수 선호 — `utility/util/misc_utility.js` 같은 기존 파일들의 스타일)에 맞춰 **가벼운
    자체 구현**을 권장. 라이브러리를 쓰면 비동기 로딩/네임스페이스 등 이 프로젝트엔 과한 기능까지 따라옴.
- 기존 `text_contents[SYSTEM_CONFIG.LANGUAGE].xxx.yyy` 참조를 전부 `t(locale, 'xxx.yyy')` 호출로 바꾸는
  작업 — Stage 1에서 이미 위치를 다 파악해뒀으니 기계적으로 치환 가능하지만, 파일 수가 많아 역시 여러
  커밋으로 나눠 진행.

### Stage 3 — locale을 실제로 어디서 가져올지 연결

- **서버(길드) 단위**: `quiz_option.js`의 `OptionStorage`(지금 서버 설정 9개 옵션을 관리하는 바로 그 구조)에
  10번째 옵션으로 "언어"를 추가하는 게 제일 자연스러움 — 이미 있는 저장/조회 패턴을 그대로 재사용.
  `server-setting-ui.js`에도 자동으로 옵션 하나 추가되는 흐름으로 들어감.
- **유저 단위(DM 전용 화면, 예: 퀴즈만들기)**: 길드 옵션이 없는 컨텍스트라 별도 저장이 필요 — 유저별 언어
  설정을 DB에 추가하거나(새 컬럼/테이블), 혹은 최초 접근 시 `interaction.locale`(디스코드 클라이언트 언어)로
  자동 추정만 하고 별도 저장은 안 하는 단순한 방식도 가능(구현 비용 대비 효과를 보고 선택).
- **기본값 추정(선택 사항)**: 유저/서버가 언어를 한 번도 설정 안 했으면 `interaction.guild.preferredLocale`/
  `interaction.locale`로 그럴듯한 기본값을 추측 → 그래도 없으면 `kor`.
- 화면 클래스들이 지금 `guild_id`(또는 `interaction`)를 생성자에서 받고 있으니, 여기서 locale도 같이
  조회해서 내려주는 흐름으로 자연스럽게 확장 가능 — 클래스 생성자 시그니처가 늘어나는 지점들은 Stage 1
  인벤토리 작업 때 같이 목록화해두는 게 좋음.

### Stage 4 — 실제 번역 콘텐츠 작성

- Stage 1~3이 끝나야 비로소 "번역만 하면 되는" 상태가 됨. 번역 자체는 기계적 치환이 아니라 문장 단위로
  자연스럽게 새로 쓰는 걸 권장(1-4에서 언급한 어순/조사 문제 때문에 원문 구조를 그대로 유지한 채 단어만
  바꾸면 어색한 문장이 나오기 쉬움).
- 슬래시커맨드 이름/설명(`command_manager.js`)은 이 봇 자체 텍스트 시스템과 무관하게 discord.js의
  `setNameLocalizations()`/`setDescriptionLocalizations()`로 별도 처리 — 여기도 이 단계에서 같이 챙기면 됨.

## 4. 리스크 / 주의사항

- **범위가 크다.** Stage 1(텍스트 이전)만 해도 90개 넘는 파일에 흩어진 문구를 옮기는 작업이라, 지금까지 진행한
  UI 개선 라운드들(파일 5~10개 단위)보다 한 자릿수 이상 큰 작업임. 화면 단위로 잘게 쪼개서 진행하지 않으면
  중간에 회귀를 놓치기 쉬움.
- **`'use strict'` 사고 재발 위험과 비슷한 종류의 함정**: 텍스트를 옮기는 기계적 작업처럼 보여도, 실제로는
  각 화면의 개행/공백(`\n\n\n` 같은 수동 레이아웃), 조사 처리, 임베드 `fields` vs `description` 구조가
  파일마다 제각각이라(1라운드에서 이미 다뤘던 문제들) 단순 복사·붙여넣기로는 안 끝나는 지점이 많음.
- **UI 클래스는 관례상 유닛테스트 대상이 아님** — 이 작업의 회귀 검증은 결국 이번 세션에서 계속 써온
  "node -e로 실제 함수 호출 시뮬레이션 + 수동 스모크테스트" 방식에 의존하게 됨. 규모가 커질수록 이 방식의
  한계도 같이 커짐 — 필요하면 이 시점에 텍스트 조회 함수(`t()`) 자체에 대한 유닛테스트(순수 함수라 테스트
  용이함)를 추가하는 걸 권장.
- **`SYSTEM_CONFIG.LANGUAGE`를 언제 없앨지 결정 필요**: Stage 2~3을 완료해도 과도기에는 "길드 옵션에 언어가
  없으면 `SYSTEM_CONFIG.LANGUAGE`를 기본값으로 쓴다"처럼 기존 상수를 폴백 용도로 당분간 남겨두는 게 안전함
  (한 번에 다 바꾸기보다 점진적 전환).
- **번역 유지보수 부담**: 언어가 2개 이상 되는 순간부터, 새 기능을 추가할 때마다 텍스트를 두 번(또는 그
  이상) 써야 함 — 이 프로젝트가 "혼자 개발/운영"이라는 점(CLAUDE.md)을 고려하면, 실제로 두 번째 언어
  콘텐츠를 계속 유지보수할 여력이 있는지 먼저 판단하고 시작하는 게 좋음. 아키텍처만 준비해두고 번역은
  나중에 필요할 때(Stage 4) 시작해도 늦지 않음 — Stage 1~3은 번역 콘텐츠 없이도 독립적으로 가치가 있음
  (텍스트 정리 자체가 유지보수성 개선).

## 5. 당장 결정이 필요한 것

실행에 들어가기 전에 사용자가 정해줘야 할 것들 (진행 지시하실 때 같이 답 주시면 계획을 더 구체화하겠음):

1. **목표가 "동시 다국어"인지 "필요시 언어 통째로 교체"인지** — 옵션 A로 충분한지, B/C까지 가야 하는지를
   가르는 가장 중요한 질문.
2. **1번이 "동시 다국어"라면, locale을 서버 단위로 관리할지 유저 단위로 관리할지**(또는 둘 다) — 저장 위치와
   UI(서버 설정 옵션 추가 등)가 달라짐.
3. **실제로 만들 두 번째 언어가 정해져 있는지**(영어가 유력해 보이지만 확인 필요) — Stage 4 번역 착수 여부와
   무관하게, 아키텍처 설계 시 "한 언어만 더 있다고 가정" vs "3개 이상도 염두" 여부에 따라 폴백 체인 설계가
   달라짐.

명시적으로 진행 지시 주시면 위 결정 사항부터 확인하고 Stage 1(텍스트 인벤토리)부터 시작하겠습니다.
