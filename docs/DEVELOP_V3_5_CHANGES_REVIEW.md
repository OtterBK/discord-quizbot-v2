## 1. 구조 리팩터 (Phase 0~6) — 모든 후속 작업의 기반 {#1-구조-리팩터}

**무엇을/왜**: `quiz_system.js` 5,959줄을 포함해 여러 대형 파일이 도메인 경계 없이 뒤섞여 있던 걸,
동작을 바꾸지 않고 클래스/도메인 경계로만 쪼갰습니다. 이후 모든 웹 연동 작업이 이 구조 위에서
진행됐기 때문에 v3.5 전체의 전제 조건입니다.

**어떻게**:
- **Facade 패턴**을 반복 적용 — 원본 파일 이름(`db_manager.js`, `utility.js`, `quiz_ui/components.js`,
  `report_manager.js`, `quiz_system.js`)은 하위 도메인 파일들을 `{...a, ...b}`로 재수출하는 얇은
  껍데기로 남기고, 실제 로직은 `db/`, `util/`, `components/`, `report/`, `quiz_system/lifecycle/`
  등 하위 디렉터리로 이동. **기존 require 경로를 그대로 유지**해서 호출부를 안 건드리는 게 핵심
  설계 원칙이었습니다.
- `quiz_system.js`는 State 패턴 엔진이라 클래스 경계 = 파일 경계로 승격(Initialize/Prepare/Explain/
  Question(+8개 하위클래스)/TimeOver/CorrectAnswer/Clearing/Ending/Finish/HOLD, `QuizSession`/
  `MultiplayerSession` 계열).
- 리팩터 원칙: **"리팩토링(이동/분리) 커밋과 버그 수정 커밋은 절대 섞지 않는다"**(`docs/
  CONTRIBUTING_REFACTOR.md`) — 이동 중 버그를 발견해도 즉시 고치지 않고 `docs/BUGS_FOUND.md`에
  기록만 하고 넘어감(위험도가 낮다고 판단된 것들). 개발자가 직접 쓴 주석은 삭제 금지 —
  코드가 옮겨지면 주석도 같이 옮기고, 코드 자체가 없어지면 `docs/DEPRECATED_CODE_REMOVED.md`/
  `docs/RELOCATED_COMMENTS.md`에 원문 보존.
- `node:test` 스캐폴딩, `eslint.config.js`(기존 코드 관행을 규칙으로 고정한 것) 이 시기에 도입.

**리스크/확인 포인트**: 이 작업 자체는 "동작 변경 없음"이 원칙이라 위험도가 낮고, 그 이후 10일간
문제 없이 안정적으로 운영됐습니다. `docs/DUPLICATE_UI_PATTERNS.md`에 발견된 UI 빌더 중복 10건은
**의도적으로 통합 안 함**(discord.js 빌더 싱글턴을 `cloneDeep`으로 공유하는 기존 패턴이 있어서,
성급하게 합치면 그 패턴이 깨질 위험 — 사용자 결정 사항).

## 2. TypeScript 점진 전환 (A-1~A-5) {#2-typescript-전환}

**무엇을/왜**: ESM 전환이 아니라 **CommonJS 유지 + TypeScript만 도입**(`module: "commonjs"`).
`allowJs: true`로 `.js`/`.ts`가 공존하게 해서 파일 단위로 점진적 전환.

**어떻게**:
- 빌드 파이프라인 구축 중 실제로 걸린 이슈들을 재현 스크립트로 원인 확인 후 해결(자원 경로 문제 —
  `${__dirname}` 기반 계산이 `dist/`로 컴파일하면 깨짐, `'use strict'` 자동삽입, `.ts`/`.js` 완전
  분리 빌드). `custom_node_modules/`(서드파티 패치 벤더링)는 전환 대상에서 의도적 제외.
- **멀티플레이 관련 파일은 맨 마지막까지 미룸** — "실전 대결(2개 이상 길드) 테스트가 안 끝난 유일한
  영역이라, 여기서 나중에 문제가 생기면 원래 버그인지 TS 전환이 만든 버그인지 구분이 안 된다"는
  이유. **이 A-3 6단계는 지금도 착수 안 함**(`docs/ACTIVE_PLAN.md` A절, 조건부 보류 중).
- `utility/`, `db/`, `managers/`, `quiz_ui/`, `quiz_system/`(멀티플레이 제외) 전체 전환 완료.
- `ts-node`(`transpileOnly: true`)로 테스트를 실행 — 타입 에러가 아니라 트랜스파일만 하고 실행하는
  방식이라, `npm run test` 통과가 `tsc --noEmit` 통과를 보장하지 않음(그래서 검증 로그에 항상 둘 다
  분리해서 표기돼 있음 — 실제로 이 세션에서도 `tsc --noEmit`이 별도로 통과 여부를 갈랐던 적이 있음).

**리스크/확인 포인트**: 이 부분은 리스크가 낮습니다(타입만 붙였을 뿐 런타임 동작 변경 없음, 10일간
무사고 운영). 멀티플레이 TS 전환이 계속 보류 중이라는 것만 인지하고 계시면 됩니다.

## 4. 편의 기능 3종 (B-2/B-3'/B-4) {#4-편의-기능}

- **B-3' 문제(단일) 복제**: 원래 계획은 "퀴즈 전체 복제"였는데 **악용 가능성 때문에 보류하고 "문제
  단일 복제"로 스코프를 줄임**(사용자 결정). 원본 데이터를 복사해 바로 다음 위치에 삽입.
- **B-4 채팅 정지/취소 알림**: 정지 사유/횟수/만료일을 밴 당사자에게 DM으로 알림. 후속 조치(취소)
  시점엔 신고 로그가 이미 삭제돼 있어서 `selectChatInfoById()`(신규 DB 쿼리)로 원문을 재조회하는
  구조.
- **B-2 문제 미리듣기**: `generatePreviewClipStream()`(ffmpeg `-c copy`, 재인코딩 없이 스트림 직접
  첨부). 당초 계획했던 UI 프레임워크 확장 대신 `interaction.reply({files, flags: Ephemeral})`로
  단순화(임시 테스트 버튼으로 직접 동작 검증 후 확정한 설계 변경).
  - **이 기능 구현 중 별개로 발견해서 같이 고친 것**: webm seek이 VBR 인코딩에서 ±3초 정확도
    오차가 나던 버그 — 이미 짜여 있었지만 **어디서도 호출되지 않던 죽은 코드**(`WebmSeeker.seek()`,
    webm 내장 Cues 테이블 기반 정확한 seek 로직)를 발견해서 실제 seek 경로에 연결. 실제 캐시 파일을
    바이트 단위로 파싱해서 검증했고, 최종적으로 **사용자가 실제 봇으로 재생해서 확인**까지 완료.

**리스크/확인 포인트**: 전부 사용자 실사용 검증까지 끝난 항목들입니다. B-2 전수테스트로 나온 피드백
12건 중 10건은 수정+검증 완료, 남은 2건(MMR 개선/랜덤 추첨 알고리즘 평가)은 "뭐가 문제인지부터

## 6. 퀴즈 선택 웹 연동 (Phase 0~4) {#6-퀴즈-선택-웹-연동}

**무엇을/왜**: 디스코드 채널을 잠그고, 웹(React+Vite)에서 퀴즈를 검색/선택하게 하는 기능. 공식
퀴즈/유저 퀴즈/랜덤(오마카세) 퀴즈/멀티플레이 로비까지 4가지 모드를 웹에서 다룹니다.

**아키텍처 핵심 결정**:
- 이 봇은 `discord-hybrid-sharding`으로 **여러 클러스터(별도 OS 프로세스)**가 떠 있는 구조라,
  "세션 상태를 어디에 둘 것인가"가 핵심 설계 문제였습니다. 답: **마스터 프로세스(`index.js`)에
  세션 상태를 두고, 기존 멀티플레이 IPC 브로드캐스트 패턴(`multiplayer_session_registry.js`)을
  그대로 재사용** — `web_session_manager.ts`가 토큰↔길드 매핑을 갖고, 클러스터→마스터는
  `WEB_SESSION_REQUEST`, 마스터→전체 클러스터는 `WEB_SESSION_SIGNAL`로 통신(`ipc_manager.ts`에
  `MULTIPLAYER_SIGNAL`과 대칭 구조로 추가).
- **세션 매니저는 스테이트리스**입니다 — 선택 내용을 세션 안에 저장하지 않고, `select`/`apply`
  요청에 실린 payload를 그대로 브로드캐스트만 합니다. 실제 quiz_info 조립은 신호를 받는 클러스터
  쪽 UI 클래스(`WebHandoffUI`, `DevQuizInfoUI` 등)가 담당. 이 설계 덕분에 Phase 2(유저 퀴즈)에서
  "한 세션 안에서 dev/user/omakase 탭을 자유롭게 오갈 수 있게" 요구사항이 생겼을 때 세션 매니저를
  전혀 안 건드리고 클러스터 쪽 분기 로직만 바꾸면 됐습니다.
- **토큰 생명주기는 한 번 재설계됐습니다.** 최초 구현은 "선택 완료 = 토큰 파기"였는데, 1차 실사용
  테스트에서 "확정 후 재선택이 안 됨"이 버그로 보고됨 → 근본 원인을 다시 논의해서 토큰 파기 시점을
  "퀴즈 실제 시작" 또는 "UIHolder 소멸"로 옮김(`closeSession`을 `applySelection`(유지)+
  `releaseSession`(조용히 파기)으로 분리). **처음엔 증상만 고치는 응급 수정으로 갈 뻔했는데, 사용자가
  세 가지 질문을 던져서 근본 설계 문제로 되돌린 케이스**입니다.
- **하이재킹 방어**: 다른 유저가 `/퀴즈`를 누르면 "권한 가져오기" 버튼 안내 → `force_take` IPC로
  홀더를 새 소유자로 교체. 이후 "권한 가져오기 직후 예전 소유자가 새 토큰을 실수로 지우는" 레이스
  버그를 나중에(Phase 5 검증 중) 하나 더 발견해서 토큰 일치 검사로 막았습니다(9번 섹션과 별개로
  Phase 5에서).
- **멀티플레이(Phase 4)만 예외**: 실제 로비 생성/참가는 마스터가 아니라 그 길드를 담당하는
  클러스터가 처리합니다(음성채널 체크에 진짜 `GuildMember`가 필요해서, `guild.members.fetch`로
  실제 조회). `createLobby`/`tryJoinLobby`가 모달 필드 읽기뿐 아니라 `interaction.reply()`까지
  의존한다는 걸 구현 중 발견해서, "페이로드 직접 대입 + 신규 static 헬퍼" 방식으로 우회했습니다.

**실사용 검증 중 발견된 실제 버그들(전부 수정+재검증 완료)**:
- 순환 require 크래시(`dev-quiz-select-ui.ts`↔`dev-quiz-info-ui.ts`) — require를 함수 안으로

## 7. 퀴즈 만들기 웹 연동 (Phase 0~5) {#7-퀴즈-만들기-웹-연동}

**무엇을/왜**: `/퀴즈만들기`(내 퀴즈 목록 → 상세 → 문제 편집)를 웹으로 옮기는 작업. 위 6번과
아키텍처는 같지만 스코프가 "길드 단위"가 아니라 **"유저(owner_id) 단위"**라는 게 핵심 차이입니다.

**아키텍처 확장**:
- `web_session_manager.ts`가 `guild`/`owner` 두 스코프를 다루도록 일반화(`scope`/`scope_id` 필드,
  `broadcast(guild_id,...)`→`broadcast(scope_id,...)` 리네임). DM은 봇-유저 1:1이라
  하이재킹 개념 자체가 없어서, guild 스코프에 있던 `already_locked` 거절 로직이 owner 스코프엔
  아예 없습니다(기존 세션이 있어도 무조건 교체).
- **실제 리팩터를 겸함**: `user-question-info-ui.ts`(파일 자체 주석에 "건드릴 엄두가 안 난다"고
  적혀 있던 가장 위험한 파일)의 인터랙션-비의존 검증 로직 7개 함수를 `quiz_editor_validation.ts`로
  순수 추출 — 디스코드 쪽 호출부를 이 모듈을 쓰도록 바꾸면서(동작 변경 없는 순수 이관), 이후 REST
  API도 같은 함수를 재사용하게 만들었습니다. **디스코드/웹 두 경로가 검증 로직을 하나로 공유**하는
  게 이 설계의 핵심 이점입니다.
- **소유권 검증 미들웨어**: `requireQuizOwnership`이 `selectOwnedQuizInfoById(quiz_id, creator_id)`로
  DB 레벨에서 소유권을 강제 — `is_private` 필터가 아니라 `creator_id = $2` 조건. 이 패턴이 오늘
  세션의 IDOR 점검에서 "이미 안전함"으로 확인된 부분입니다(위 IDOR 정정 설명 참고).
- **설계 결정으로 스코프를 줄인 것들**: 이미지/오디오는 URL 입력만(파일 업로드 없음), 오디오
  미리듣기는 ffmpeg 클립 대신 유튜브 `?t=` 타임스탬프 링크로 대체(새 스트리밍 엔드포인트 불필요),
  문제 CRUD는 디스코드 3-모달과 달리 단일 PUT/POST로 통합.

**실사용 검증 중 발견해서 고친 것들**:
- OX/객관식 정답 미선택 시 서버 에러 코드(`invalid_answers`)가 raw 문자열로 그대로 노출되던 버그.
- "권한 가져오기" 직후 예전 소유자가 새 토큰을 실수로 지우는 레이스 버그(위 6번에서 언급한 것과
  같은 클래스의 버그, owner 스코프에서 재발견 → `releaseSession`에 토큰 일치 검사 추가로 수정,
  회귀 테스트 포함).
- UI 피드백 3라운드(Phase 4) — 승인된 목업의 설계(문제 목록 카드 시인성, "실제 디스코드에선 이렇게
  보여요" 미리보기)를 초기 구현이 상당 부분 놓쳤던 걸 사용자가 지적해서 재작업. **미리보기 패널을
  "Phase 0 데모 전용"으로 잘못 스코프아웃했던 계획 오류를 사용자가 잡아준 사례**입니다.

**검증 상태**: `docs/TEST_CHECKLIST.md` T/U/V/W 섹션 — Phase 3/4/5는 **사용자가 실제 Discord+
브라우저로 처음부터 끝까지(목록→생성→편집→CRUD 전부) 확인 완료**, 발견된 버그도 그 자리에서
수정+재검증까지 끝났습니다. 2클러스터 이상 강제 실행 환경에서의 relay 검증(디버그 로그로 실측)과
GC 세션 만료 시나리오(15분 대기)도 실제로 확인했습니다. **이 기능이 이번 v3.5에서 가장 철저하게
검증된 부분**입니다.

## 9. 문제 미리보기 마크다운 + 웹 API 보안 강화 {#9-마크다운-보안강화}

오늘(2026-08-12) 세션에서 진행한 작업입니다. 상세는 이미 별도로 보고드린 내용과 동일하므로 요약만:

- **마크다운**: 문제 편집 웹 미리보기(`questionDisplay.jsx`)가 문제/힌트/정답 텍스트를 plain text로
  렌더링하던 걸 `react-markdown`+`remark-breaks`로 실제 디스코드와 동일하게 서식 적용.
- **Rate limiting**: 원래 전혀 없었음 — `express-rate-limit` 도입(현재 조회 초당 10회/쓰기 초당
  8회, 오늘 중 두 번 조정됨).
- **IDOR 라이브 검증 보강**: `/api/my-quizzes` 소유권 체크를 두 개의 실제 세션으로 교차 접근
  시도하는 테스트로 보강(단, 이건 "편집 API"만의 얘기였고 "선택/플레이 API"의 빈틈은 못 봤다는 게
  위에서 정정드린 내용).
- **백엔드 검증 구멍 2개**: `answer_type` 화이트리스트 누락, 비문자열 입력이 서버 검증을 통째로
  건너뛰던 문제(가장 심각했던 건 타입 체크 없이 `.trim()`을 호출해서 TypeError로 요청이 죽을 수
  있었던 경로).
- **[가장 심각] SQL 인젝션**: 랜덤/멀티플레이 퀴즈함 모드의 `basket_items`가 서버 검증 없이
  `WHERE quiz_id IN ${...}` 문자열 보간까지 도달할 수 있었던 실제 취약점 — `= ANY($1::int[])`
  파라미터화로 수정. 영향 분석은 별도로 이미 보고드렸습니다(DB 커넥션 풀이 5개뿐이고 타임아웃이
  없어서 DoS 임팩트가 특히 컸다는 내용).
- **아직 안 고친 것**: `basket_items`의 quiz_id에 소유권/공개여부 검사 자체가 없어서, 다른 유저의
  비공개 퀴즈도 quiz_id만 알면(추측/열거 가능) 게임에 출제될 수 있는 문제 — 다음 세션 TODO 1번.

## 10. 오늘 추가로 발견/수정한 것 (이 문서 작성과 같은 세션) {#10-오늘-발견}

`PG_MAX_POOL_SIZE` 조정을 검토하다가 우연히 발견한 것들입니다:

1. **[심각, 수정 완료] 마스터 프로세스가 DB를 초기화한 적이 없었습니다.** `index.js`가
   `db_manager.initialize()`를 호출하지 않아서, 마스터에서 직접 DB를 호출하는 라우트들
   (`/api/my-quizzes/*`, `/api/user-quizzes`, `PUT /api/server-option`)이 전부 조용히 실패하고
   있었을 가능성이 있습니다. `bot.js`와 동일한 방식으로 `index.js`에도 초기화 호출을 추가했습니다.
   **이게 위 7번 섹션의 "사용자가 실제로 다 확인했다"는 기록과 모순되기 때문에, 다음에 봇을
   재시작하시면 퀴즈 만들기 웹에서 저장/생성이 실제로 잘 되는지 한 번 확인해주시면 좋겠습니다.**
   제가 직접 봇을 띄워서 재현할 방법이 없어 코드 분석만으로 내린 판단입니다.
2. **[경미, 수정 완료] DB 연결 테스트 코드가 커넥션을 하나 반납 안 하고 있었습니다**
   (`pool.connect()`의 `release()` 콜백 누락) — 프로세스당 풀 슬롯 하나가 영구적으로 낭비.
3. **`PG_MAX_POOL_SIZE`를 5→20으로 올렸습니다.** 참고: 이 값은 **프로세스마다 각자 적용**됩니다 —
   마스터 1개 + 클러스터 N개(`totalClusters: 'auto'`, 길드 수에 따라 자동 증가)가 각각 자기만의
   풀을 갖기 때문에, 실제 총 DB 커넥션 수는 `20 × (1 + 클러스터 수)`입니다. 클러스터가 늘어나면
   Postgres 서버의 `max_connections`(기본 100)에 부딪힐 수 있으니, 봇이 커지면 이 값을 다시
   낮추거나 Postgres 쪽 설정을 같이 올려야 할 수 있습니다.
