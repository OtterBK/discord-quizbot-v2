# 디스코드 UI 분리 전수 점검 작업계획서

> 2026-08-18 작성. **이 문서는 점검 방법론/범위/기준만 정한다 — 실제 점검(파일별 판정)과 구현은
> 다음 세션에서 진행.** 계기: `QUIZ_BASKET_PRESET_UI_PLAN.md`의 퀴즈함 기능 설계 중, 메인 화면
> (`OmakaseQuizRoomUI`)의 컴포넌트 행 예산이 5/5로 꽉 차서 새 기능을 못 넣는 문제를 발견 → "독립
> ephemeral 화면으로 분리"하는 새 해결 패턴을 확정. 이 패턴이 다른 화면에도 적용할 만한지, 전체
> `quizbot/quiz_ui/` 를 훑어서 후보를 찾기로 함.

## 목표

`quizbot/quiz_ui/*.ts` 화면들을 순회하며 "지금 한 화면에 너무 많이 몰려있어서, 분리하면 더 깔끔해질
후보"를 찾아 목록화하고 우선순위를 매긴다. **이 문서 자체는 후보 발굴 방법론만 정의 — 실제 순회/판정은
다음 세션 작업.**

## 새로 확정된 분리 패턴 (재사용 기준)

`QUIZ_BASKET_PRESET_UI_PLAN.md`에서 처음 설계한 패턴, 조건에 맞으면 재사용:

**독립 ephemeral 화면 분리** — 서브 기능을 메인 화면의 `QuizbotUI`/`UIHolder` 스택에 끼워넣는 대신,
`interaction.reply({ephemeral:true, ...})`로 최초 응답을 만들고 그 안의 컴포넌트는
`interaction.update()`(discord.js가 제공하는 "이 컴포넌트가 속한 메시지 자체를 편집"하는 API, 현재
`quiz_ui/` 전체에서 미사용 확인됨)로 자체 갱신하는 독립 플로우. `admin-panel-ui.ts`의
`report_manual_processing.sendReportLog`(버튼 클릭 시 UI 전환 없이 자체적으로 응답까지 처리하고
끝나는 기존 패턴)와 같은 계열 — 완전히 새로운 개념이 아니라 기존 관행의 확장.

**적용 조건 (둘 다 만족해야 후보)**:
1. 서브 기능이 메인 화면과 독립적으로 완결되는 흐름인가(자기 안에서 보고, 고르고, 실행까지 끝남 —
   메인 화면의 다른 상태를 계속 참조할 필요가 없는가). 아니면 메인 화면 흐름에 깊이 얽혀있어서 분리가
   오히려 왔다갔다하는 번거로움만 늘리는가.
2. 메인 화면의 컴포넌트 행 예산이 이미 빠듯한가(4~5/5), 또는 select menu가 25개 한도에 근접/도달해
   있는가 — 둘 다 "지금 이 화면에 너무 많은 게 몰려있다"는 직접적 신호.

**주의(설계 중 발견한 함정)**: 독립 화면으로 분리하면 두 메시지(메인 persistent 화면 vs 분리된
ephemeral 화면)가 완전히 독립적이라, 서브 화면에서 뭔가 바뀌었을 때 메인 화면에 자동으로 반영되지
않는다. 분리 후보로 확정하는 화면마다 "메인 화면 어느 텍스트/카운트가 이 서브 기능 때문에 stale해질
수 있는지"를 미리 따져보고, 필요하면 메인 화면 인스턴스 참조를 클로저로 들고 있다가 변경 시점마다
직접 `main_ui.update()`를 호출하는 동기화 코드를 같이 설계해야 함(`QUIZ_BASKET_PRESET_UI_PLAN.md`의
"메인 화면 동기화" 섹션이 실제 사례).

## 판별 기준 (분리 후보를 어떻게 알아보나)

1. **컴포넌트 행 예산 압박**: Discord 메시지당 액션로우 5개 한도에 근접/도달한 화면. `initializeComponents`/
   `setUpXXXComponent`류 메서드에서 조건부로 붙는 행이 몇 개까지 겹칠 수 있는지 worst-case로 세어볼 것
   (퀴즈함 사례처럼 "지금은 여유 있어 보여도 조건 조합에 따라 5/5까지 찬다"가 실제로 있었음).
2. **한 화면 안에 서로 다른 관심사가 섞여있는 경우**: 예) 퀴즈 진행 설정 + 퀴즈함 관리 + 태그 선택이
   전부 한 클래스(`QuizInfoUI` 계열)에 들어있던 것처럼, 논리적으로 독립적인 기능 여러 개가 한 화면의
   버튼 맵(`quiz_info_ui_handler` 같은)에 뒤섞여 있는 경우.
3. **이미 문서화된 복잡도 경고 신호**: `quiz_ui/CLAUDE.md`나 파일 자체 주석에 "복잡하다"/"건드리기
   무섭다"고 이미 적혀있는 화면 — 아래 "1차 후보" 참고.
4. **select menu가 25개 한도 근처**: `MAX_SELECT_OPTIONS`류 상수나 "최대 25개까지만" 주석이 있는
   화면 — 데이터가 늘어나면 퀴즈함과 같은 문제가 생길 잠재 후보.

## 1차 후보 (기존 문서/주석 기반 예비 목록 — 재검증 필요, 순회 전 참고용으로만)

이미 알려진 신호를 근거로 뽑은 예비 목록. **실제 순회 없이 만든 초안이라 다음 세션에서 파일을 직접
열어 위 기준으로 재검증할 것** — 우선순위 판단의 출발점일 뿐 확정 아님.

| 화면 | 알려진 신호 | 비고 |
|---|---|---|
| `quiz-info-ui.ts`/`omakase-quiz-room-ui.ts` | 컴포넌트 행 예산 5/5 (실측 완료) | ✅ 퀴즈함 부분은 이미 분리 설계 끝남(`QUIZ_BASKET_PRESET_UI_PLAN.md`) — 나머지(태그 선택 등)도 비슷한 문제 있는지 재확인 |
| `multiplayer-quiz-lobby-ui.js` | `quiz_ui/CLAUDE.md`에 "IPC 기반, 가장 복잡"로 명시 | 다만 복잡도 원인이 IPC 신호 처리 로직이지 컴포넌트 행 개수가 아닐 수 있음 — 이 문서의 "분리" 기준과 다른 종류의 복잡도일 가능성, 재확인 필요 |
| `user-question-info-ui.ts` | 파일 자체 주석 "건드릴 엄두가 안난다... 우선 돌아가면 장땡" | 문제 편집기 — 오디오 구간/이미지/정답/힌트/타이머 등 관심사가 많이 섞여있어 보임 |
| `user-quiz-info.ui.ts` | 퀴즈 상세+편집+공개전환+삭제(일반/관리자 분기)+웹 재적용 로직까지 한 클래스 | 관심사 개수 기준으로 후보 |
| `web-handoff-ui.ts` | dev/user/omakase/multiplayer 4개 모드를 한 클래스가 전부 처리 | 컴포넌트 행 문제가 아니라 "한 클래스가 너무 많은 모드를 안다"는 다른 종류의 비대화 — 이 문서 범위에 넣을지 별도 판단 필요(코드 조직 문제 vs UI 화면 문제) |

**참고 사례(반면교사 아님, 좋은 예)**: `admin-panel-ui.ts`는 이미 각 기능(밴 목록/신고/퀴즈 관리/공지
관리/점검 모드/시즌 관리)을 전부 별도 화면 클래스로 분리해뒀음 — 이 문서가 지향하는 방향을 이미
잘 하고 있는 기존 사례로 참고할 것.

## 점검 방법 (다음 세션 진행 순서)

1. `quizbot/quiz_ui/*.ts` 전체를 순회 — 위 1차 후보부터 먼저, 나머지 파일도 훑기(단순 정적 화면
   `alert-quiz-start-ui.js`/`note-ui.ts` 같은 건 빠르게 "해당 없음" 처리하고 넘어가면 됨).
2. 각 화면마다: (a) `initializeComponents`류 메서드에서 조건부로 붙는 행을 worst-case로 세기, (b) 그
   화면이 담당하는 "관심사" 개수 나열, (c) 위 4개 판별 기준 중 몇 개에 해당하는지 체크.
3. 후보로 확정된 것마다: 분리했을 때 뭘 독립 화면으로 뺄 수 있는지, "적용 조건 2가지"를 만족하는지,
   메인 화면 동기화가 필요한 지점이 어디인지 1~2줄로 메모.
4. 결과를 이 문서에 "점검 결과" 섹션으로 추가하거나, 항목이 많으면
   `docs/archive/DUPLICATE_UI_PATTERNS.md`(기존 유사 사례 — 중복 UI 패턴 후보 10건을 발견만 하고
   통합은 보류해둔 문서)와 같은 성격의 별도 문서로 분리 — "발견만 하고 바로 다 고치진 않는다"는
   점에서 그 문서와 동일한 취급.
5. 우선순위(적용 순서)는 후보 목록이 나온 뒤 사용자와 협의해서 정함 — 전부 한 번에 고치지 않을 가능성
   높음(기존 `DUPLICATE_UI_PATTERNS.md` 사례처럼 "발견은 했지만 통합/적용은 보류" 결론이 나는 항목도
   있을 수 있음).

## 범위 밖

- 웹 UI 쪽 레이아웃/UX (이번은 디스코드 한정).
- 실제 코드 분리 작업(이 문서는 방법론+예비 후보만, 적용은 각 항목 확정 후 별도 진행).
- `QUIZ_BASKET_PRESET_UI_PLAN.md`(퀴즈함 건)는 이미 설계가 끝나 별도 문서로 진행 중이므로 이 전수
  점검의 결과물로 다시 다루지 않음 — 이 문서가 확립한 패턴의 최초 적용 사례로만 참조.
